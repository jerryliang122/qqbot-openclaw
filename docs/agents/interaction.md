# 交互面：ask_user 按钮、Secret 输入、Webhook 派发

> 深度参考文档。改按钮卡片 / 凭据输入 / webhook 传输前必读。

- **webhook 模式的 op:0 派发必须挂 detached 准入根，且「光包 `runDetachedWebhookWork` 不够」（2026-10-30 修复，issue #74）**：SDK `WebhookTransport.handleRequest` 对 op:0 是「先 ACK、后台 fire-and-forget 派发」（防平台重投超时），插件拿不到那条派发 promise；而 openclaw 对每个 HTTP 请求持一次 root-work 准入（route-auth `runWithGatewayHttpWorkAdmission`，插件路由 handler settle 即释放），后台派发链经 AsyncLocalStorage **继承的是这个已释放的请求根** → 框架 enqueue 处 `isGatewaySubordinateWorkAdmissionClosed()` 判 `current.released === true` → `GatewayDrainingError`（报错文案是四分支的兜底句「temporarily unavailable」，**网关并没有 drain**；websocket 模式的准入挂在常驻连接上故无恙；无根上下文反而放行——判定只对「有根且已释放」关闸）。修法：`src/adapter/webhook.ts` 的 op:0 委托放进 `openclaw/plugin-sdk/webhook-request-guards` 的 `runDetachedWebhookWork` 回调（2026.10.5 基线即有该子路径；共享加载器/降级在 `src/features/detached-webhook-work.ts`，模块在而**导出缺失也要 WARN**，不静默失效），回调内再**等「本次委托派生的在途派发」全部落地**才 settle——detached 根只在回调挂起期间保持引用，而 SDK 的 fire-and-forget promise 不在回调的 AsyncWorkScope 里（scope 的 pending 集合只收显式注册的 promise），**不等的话 detached 根随 ACK 释放、bug 原样复现**（issue 建议的「选项 1 直接包裹」正是不够的形态）。在途登记在 `src/features/webhook-dispatch-tracker.ts`：消息路径 = QQBotGateway（webhook 模式）包裹 bot 实例的 `handleInboundMessage`（TS-private、实例属性晚绑定，SDK 的 `this.handleInboundMessage(raw)` 运行时查表；缺失 WARN 退化为修复前行为）——SDK 的 handleDispatch → onMessage → handleInboundMessage 发生在委托调用的**同步级联**里，包裹即保证「委托期间同步登记」；interaction 路径 = `createInteractionDispatchListener`（网关真实接线，导出供测试）。**两个承重的 SDK 语义前提**：① 上述派发级联在 handler 调用的同步段内启动（晚绑定实例属性查表）；② `QQBot.emit` 覆写为**逐个 await listener promise**（`handleInboundMessage` 的 downstream 是 `await this.emit(...)`）——登记条目的 settle 时点因此覆盖完整消息处理。SDK 若改为 emit 不 await，登记会「早 settle」、根提前释放——运行时 tripwire 探测不到这种漂移（它只看零登记），由测试层锁定（tests 里「listener 挂起期间登记表不应归零」断言，SDK 换版时先跑该文件）。**相关性用 scope 圈定**（Sourcery 评审后从 marker 改版）：`beginWebhookDispatchScope()` 后**同步**调委托——JS 单线程下同步级联里的登记恰好属于本请求，同步段一结束立刻 `end()`，并发请求各自持根互不搭车（marker/按账号过滤会把同账号并发请求的条目也等上）。**登记 settle 后留 tombstone 计数 + 永不 settle 的卡死条目 FIFO 上限**（各 64/账号）：秒完成的派发（guard 拦截等）也算本请求的工作，立即出表会让快照漏拍、tripwire 误报；settle 的 race timer 在 finally clearTimeout。**委托失败且响应未写出必须兜底 500**——响应写出权在 detached 回调手里，外层 catch 看不到拒绝，不写就悬挂到平台超时；三类失败形态都要兜：委托同步抛错/异步 reject/超时（delegate 本身也 race 持有上限——SDK handler 挂死时回调要能走到 settle），以及 `runDetachedWebhookWork` **自身拒绝**（全局 drain 下新根被拒、回调未执行、无 ACK）——外层 catch 一并 `onDelegateError`（writeErrorResponse 有 headersSent 防重复写）。**降级路径（handleSimple）必须先自行验签再委托**：顺序试 handler 的话第一个 `await` 之后 scope 已收口，同路径第 2+ 个账号的派发登记不进 scope、detached 根随 ACK 释放（镜像 ingress 路径的显式验签）。持有上限默认 360s 且是**总预算**（delegate race 与登记表 settle 共享同一 deadline——两段各计一份串行跑满会让根挂到 720s、restart drain 等 2 倍；两段的 race timer 都在 finally clearTimeout，Promise.race 不取消落败方、不清理的话每个请求遗留一个挂满上限的定时器；覆盖群合批 maxHoldMs 300s 兜底 + dispatch；`QQBOT_WEBHOOK_DISPATCH_HOLD_MS` 覆盖）——超限放弃持有，未入队工作以无根身份继续（**有界权衡**：>360s 才到 enqueue 的直发链会退回修复前行为、用户收到失败兜底文案；群合批这条唯一合法长路径的冲刷有自己的根，见下）。**群合批的批次派发（onFlush 的 completion）也要包 detached 根——且必须包在这一层**：这是 maxWait 兜底定时器（直接调 onFlush，不经过 flushGroupMergeQueue）、busy 归零显式 flushKey、退出冲刷的全部咽喉；冲刷运行在「上一轮 dispatch 的延续 / 定时器」上下文里，继承的根可能已释放（尤其 maxHoldMs 配 >360s 时 webhook 请求根先到期），webhook 模式下批次 enqueue 会被拒（用户丢消息）——`withDetachedWebhookWork` 在继承根缺失/已释放时给批次全新独立根（websocket 模式继承根本就常活，行为等价；真处 drain 时新根被拒 = 与不包时的 enqueue 拒绝同结果，无退化）。tripwire：应派生派发的事件类型（`DISPATCH_PRODUCING_EVENT_TYPES`）零登记 → WARN（SDK surface 漂移的唯一信号）。守卫 `tests/webhook-detached-dispatch.test.ts`（25 例，含**用真实 openclaw dist 准入状态机的 money test**：fire-and-forget 链在根释放后判 closed=true 复现病灶、detached 回调内 await 工作期间判 closed=false 锁修法；真实 SDK WebhookTransport + 合法 Ed25519 签名端到端；网关 interaction 接线；默认 loader 生产路径）+ sdk-surface 对 `runDetachedWebhookWork` 的名级断言（属性访问对扫描器不可见）。另：SDK webhook 模式对 `dispatchEvent` 返回 `action:"raw"` 的事件无处理分支（静默丢弃，`bot.on('rawEvent')` 在 webhook 下收不到东西）——既有局限，与本修复无关。

- **ask_user buttons**: single-question prompts render one inline keyboard (`qqbot:q:` button_data) resolved via `questionGatewayRuntime.resolveOption`. Multi-question prompts (2-3 questions) arrive **text-only** (the framework's v1 contract: no structured options in `channelData.askUser`); the plugin parses the prompt text (`parseMultiQuestionPrompt`) and buffers taps in an in-memory store. **c2c 单聊走顺序发题**（逐题收集，最后一题卡即提交点，见下方 PR2 段）；**群聊走旧路径**：一次发出全部题卡（`qqbot:qm:<recordId>:<qIdx>:<oIdx>`），集齐后发一张 **confirm card**: an instruction button (`action.type=2`, `enter: true`) whose data is the full keyed answer text (`"1: 3\n2: 1"`), which the QQ client emits as a **real user message** — the framework's native keyed-text claim then resolves the pending ask_user. A second `enter: false` button pre-fills the input for manual editing. **Never** submit multi-question answers programmatically: official openclaw has no multi-question submit API for channels (maintaining a fork costs more than it buys), and synthesizing an inbound user message fails because the framework steers it into the ask_user-suspended run without claiming the question (2026-08-24 incident). Inbound text is **buffered locally during multi-question answering** (red line redefined 2026-11-11, issue #99 / PR #100) — while a multi-question pending is armed (**c2c only**), inbound text is consumed by the plugin as the answer to the *current* question and is **not forwarded to the framework**: the QQ platform cannot tell a user-typed message apart from an instruction-button callback payload (both arrive as ordinary inbound messages), and forwarding mid-flow text only hits the framework's `validateAnswers` partial rejection + re-ask loop. Only after **all** questions are answered does the plugin emit the full keyed answer as a **client-generated real user message** (`type=2` + `enter=true`) for the framework to claim. Boundaries: multi-question pending armed + c2c only; single-question pending / no pending ⇒ text still reaches the framework untouched; slash commands (`/`) still pass through as an escape hatch. Classification is **by shape only** (a callback payload is always the plugin-generated keyed form `"N: v"` × N lines; anything else is user-typed) — never by guessing the user's intent from intermediate wording. Parse failures (secret/malformed) fall back to plain text. Display: button labels are truncated (`buildButtonLabel`, ~12 CJK chars) with full options in the card body; rows auto-split when labels are wide. `isOther` questions (detected via the "Other: reply..." line) get a `✍️ 其他` **instruction button** (`action.type=2`, pre-fills `"N: "` in the client input box) so free-text answers are one tap + typing away. **出站锚点（2026-11-05）**：问题卡（单题卡 / 多题卡 / 确认卡 / 状态回执）一律走 `outbound-service.sendText` + **本轮 inbound 的显式锚点**（`envelope.messageId`）⇒ 被动回复——不耗每日 1000 条主动预算，用户关闭「允许主动发送」时也能收到问题（此前走 SDK 直发，不带 `msg_id` ⇒ 平台按主动消息处理，卡片根本发不出去，模型只能空等到 ask_user 超时）。锚点不可用（TTL 过期 / 平台判死 40034005·40034128）⇒ **降级为主动发送一次**（`src/outbound/question-send.ts`，同进度卡口径）。多题的续卡 / 确认卡 / 状态回执复用登记在 pending 里的**同一锚点**（`getPendingMultiQuestionAnchor`）。**红线：禁止改回 SDK 直发（`bot.sendTextWithKeyboard`）**；也**不得**让网关的 `retryOnDeadAnchor` 兜底——那条主动重发路径不携带 keyboard，用户会看到题干却无从作答。 **单题卡自渲染（2026-11-05，issue #93 PR1）**：单题此前**不重绘**，直接把框架 `payload.text` 原文当正文发出去 ⇒ 用户看到的是 3 行框架英文脚手架（`Question for you:` / `Other: reply with your own answer.` / `Reply with the number…`）+ 与按钮重复的选项清单，且按钮标签既不截断也无序号前缀。现改为**插件自渲染**，与多题卡同构：正文 = `**<header>**` + 题干 + `**1.** 选项 —— 描述` + `👇 点下方按钮作答` + （`isOther` 时）`不想选按钮？直接回复「序号 / 选项名 / 你的答案」`；按钮 = `① ②` 前缀 + `buildButtonLabel` 截断 + 自适应分行（`qqbot:q:<recordId>:<optIdx>` 回调契约**不变**）。渲染层落在 `src/features/question-card.ts`（单题 / 多题共用；多题渲染输出**逐字未变**，既有回归用例即迁移安全证据）。单题文本反解 `parseSingleQuestionPrompt` 以 `channelData.askUser.optionValues` 的**精确 label** 为锚点（比多题解析器的结构推断稳）；**解析失败一律返回 `null` ⇒ 回退到「框架原文 + 旧键盘」= 改造前形态，零回归**。单题**不加**「✍️ 其他」按钮（单题答案 = 用户整条文本，预填前缀会污染答案），自由作答靠正文那一行引导。**卡片发送失败后的纯文本兜底**以 `keyboardAttached: false` 重渲正文（2026-11-05 评审 F1）：去掉「👇 点下方按钮作答」、引导行改为「直接回复「序号 / 选项名（/ 你的答案）」」——键盘没发出去，正文不得指引用户点不存在的按钮；解析失败（`parseSingleQuestionPrompt` 返回 null）的兜底仍走「框架原文 + 旧键盘」形态。 **单问题 pending + c2c 旁路（PR1）**：单题卡正文明确引导「直接回复」，而 c2c 入站有 3s 防抖合并（合并会把答案改写成 `[消息 i/N]` 分节体 ⇒ 框架认领到的答案被污染）⇒ 单题卡发出后登记一条 pending（`registerPendingSingleQuestion`，**仅 c2c**，会话键含 accountId，TTL 25min），让该会话的下一条文本**不被合并**（`inbound-debounce.ts` 旁路，与多题 keyed 答案同款机制）；`secret-capture` 中间件同样在 pending 期间**放行**（答案文本绝不能被当成密钥值吞掉，红线）。pending 清理：按钮 resolve 成功 / 卡片发送失败 / 该会话下一条入站消息 / TTL 兜底。群聊**不登记**单问题 pending（群合批旁路未动，群行为与改造前一致）。 **多题 c2c 顺序发题（2026-11-06，issue #93 PR2，**仅 c2c 单聊**）**：多题此前一次性把 2–3 - **多题问答进行中（issue #99 / PR #100，2026-11-11）：文本本地暂存 + pending 置终态 + 副本丢弃**——**红线再界定**：多题 pending 武装期间（**仅 c2c**）的入站文本**一律由插件本地暂存为当前题答案，不转发框架**。**为什么**：QQ 平台无法区分「用户手打的普通消息」与「指令按钮代发的回调内容」——两者都是普通入站消息；中间态文本转发给框架只会撞上 `validateAnswers` 的 partial 拒收 + 重问循环（白烧一轮、两侧状态分裂），且靠中间态词汇猜用户意图必然失效（答题中途完全可能问别的）。**分类只认形态**：回调载荷恒为插件自己生成的 keyed 形态（`"N: v"` × N 行），非 keyed 即用户手打 ⇒ 形态匹配是唯一判据。**边界**：仅多题 pending 武装期间 + 仅 c2c；单题 pending / 无 pending 时文本照旧原样转发框架；斜杠命令（`/` 开头）照旧放行（逃生通道）。**文本作答流程**：单行文本 → 记为**当前题**答案（cursor 前进、续发下一题卡）；末题收齐 → 发**文本作答确认卡**（单「✅ 提交」按钮携带全量 keyed；keyed > 300 字符时不挂按钮、只剩可复制手打模板）；多行但不可认领（半成品模板）→ 消费 + 引导回执；纯附件 / 斜杠命令 → 照旧走原路径。**机制三层**：① 放行判定处（`inbound-debounce.ts` 的 `shouldDebounceC2CItem`）**同步认领**全量 keyed 作答 ⇒ pending 置终态 + 登记答案文本；② 入队口（`enqueueC2CInboundMessage`）丢弃**逐字副本**（同文本 + 不同 messageId + 10s 窗口）——连点 / 平台重推的副本既不成轮也不进防抖缓冲（降级进缓冲后单条 flush 仍是一轮，助手会多回一条雷同消息）；③ `dispatch.ts` 起点保留**兜底认领**（防抖关闭配置不经 `shouldDebounce`）。**认领形态与框架对齐**：框架 ask_user 归一化对每题强制 `isOther: true` ⇒ 值只要非空即可（越界数字 / 多值 / 任意文本都被当自由文本收），插件认领口径与之逐项对齐。**提交按钮防连点**：末题选项与群确认卡「✅ 提交」带 `click_limit: 1`（每次点击都让客户端代发整份答案文本，连点 = 同一份作答重复投递）；`enter: false` 的预填型按钮（「✍ 其他」「✏ 改一改」）**不设**（重复点无害，清空输入框后再取模板是真实用法）。

- **Secret input flow** (`qqbot_secret_input` tool, c2c only): AI calls the tool with an env var `name` → plugin sends a card (with a `取消` instruction button) and registers a one-shot pending (`src/features/secret-input-store.ts`, TTL 10min, keyed `accountId:c2c:<openid>`) → the user's next c2c text message is **intercepted** by the `secretCapture` middleware (`src/middleware/secret-capture.ts`, mounted after slashCommand、before c2cTypingIndicator — 旧邻接的 groupMessageCoalescer 已随内建 coalescer 删除) and executed via `openclaw secrets store set` (`src/features/secret-store-cli.ts`) — the message never reaches the framework (the secret must never enter the AI transcript). Kind is **always `env`** (agent-readable environment value, written via `--value`): openclaw 2026.9+ splits the store into agent-readable env vs protected write-only secrets, and a chat-card value is both already exposed in QQ history and needed readable by the AI afterwards — storing it as `secret` made it unusable (2026-08-30 user feedback). The executor's secret/stdin branch is retained as generic capability with no current callers. The plugin composes the command (spawn + args array, `shell` never used); the AI only supplies the name (validated `^[A-Z][A-Z0-9_]{0,127}$`). Cancel keywords (`取消`/`cancel`/`#cancel`/`/cancel`) abort; empty messages keep waiting. **Red line**: the capture middleware yields (passes through) whenever a multi-question ask_user is pending for the same conversation — ask_user answer messages must never be swallowed. After a successful write the plugin best-effort runs `openclaw secrets reload`. Known accepted trade-offs: (1) openclaw's plugin install scanner logs a *critical* `dangerous-exec` warning for the `node:child_process` spawn — local installs are NOT blocked (hard blocks are dependency-name denylist only); (2) the spawned CLI must be the **same openclaw install as the running gateway** — `resolveOpenClawCli()` resolves from `process.argv[1]`'s package root first, then `require.resolve('openclaw')`, then PATH. Never let it fall back to the repo's pinned dev copy when the gateway is the global install: state-DB schema is owned by the gateway's version and an older CLI refuses the write (2026-08-30 incident: dev copy 2026.8.1-beta.3/schema 9 refused the global 2026.9.1/schema 12 DB, exit 1); (3) secrets inevitably remain in the user's QQ chat history — the card copy warns about this.
