# 配置面、凭据与能力声明

> 深度参考文档。改配置类型 / 凭据读取路径 / 通道能力声明前必读。

- **`messaging.inferTargetChatType` 必须实现（2026-10-20 接入 10.5 通道契约）**：宿主做「隐式 owner 心跳投递」时依赖通道**直接给出目标对应的会话类型分类**（`inferTargetChatType: ({to}) => ChatType | undefined`）——通道不提供时宿主只能走通用路由搜索，Gateway 状态会一直报 `waiting for route`。本插件在 `src/messaging-adapter.ts` 提供，语义由 `src/outbound/target.ts` 的 `inferQQBotChatType` 决定：`qqbot:c2c:*` / 裸 openid → `direct`，`qqbot:group:*` → `group`，**其余一律 `undefined`（不猜）**——QQ 频道（`qqbot:channel:*`）本插件不支持（`tryParseTarget` 返回 null），猜成 `direct` 会把路由带偏。

- **`config.inspectAccount` 是只读巡检面，不 materialize 运行期凭据（2026-10-20 接入）**：`resolveAccount` 是运行期路径，允许假设凭据已就绪并快速失败；而 `openclaw status` / `openclaw channels status` / doctor / config 修复等**只读命令路径**不该为了「描述配置」而触发 token 交换或扫码登录。`src/config.ts` 的 `inspectQQBotAccount` 只描述状态（`appIdSource` / `appIdStatus` / `secretSource` / `secretStatus`），凭据走 SecretRef/文件但当前路径取不到时上报 `configured_unavailable` 而非谎报「未配置」或直接抛错。**注意 `secretStatus` 的三态语义**：`available`=已 materialize、`configured_unavailable`=已配置但当前只读路径取不到、`missing`=未配置。

- **`clientSecretFile` 曾是「声明了但从不读取」的死配置（2026-10-20 修复）**：`resolveQQBotAccount` 此前只把 `secretSource` 标成 `"file"` 却把 `clientSecret` 留空 → `resolveDefaultQQBotAccountId` 认为该账号「可运行」并选中它（`accountShapeRunnable` 的 `hasSecretSource` 含 `clientSecretFile`），但网关启动时又因 `clientSecret` 为空直接放弃（`gateway/lifecycle.ts`），用户表现为「配了文件凭据却静默起不来」。**修复后的设计（经 Sourcery 评审 2 轮修正，勿走回头路）**：**(a) `resolveQQBotAccount` 全程不读盘**——它是热路径（每次出站发送都解析一次账号），同步 `stat`/`readFileSync` 会阻塞事件循环（网络挂载上可能卡死整机），且只读巡检路径不该 materialize 凭据；文件只在**账号启动时读一次**（`gateway/lifecycle.ts` 的 `materializeQQBotAccountSecret`）。**(b) 内联密钥与凭据文件强制互斥**——两者同时存在时内联优先、文件被**静默忽略**，写入时必须清掉另一个（`resolveCredentialFields`）。**(c) 注销要清 `clientSecretFile`**——只清内联的话账号仍能用同一份文件凭据起来，等于没注销。**(d) `isConfigured` 语义三处对齐**（`channel.ts` / `setup/finalize.ts` / 巡检）：`secretSource === "file"` 且配了 `appId` 即视为已配置，否则已配好文件凭据的账号会被误判为未配置、被拉去重新扫码。**(e) 读盘缓存按 `mtimeMs + size + ino` 判定**——只看 mtime 会在「轮转密钥但沿用旧 mtime」（备份还原 / `cp -p` / 某些挂载的时间精度）时读到旧值。

- **`capabilities.tts.voice` 必须声明，否则 TTS 被当普通音频文件发（2026-10-20 接入）**：框架据此决定合成目标（`resolveTtsSynthesisTarget`：未声明 → `audio-file`）与「是否原生语音条」（`supportsNativeVoiceNoteTts` / `supportsTranscodedVoiceNoteTts`）。本插件 TTS 走 **SILK 语音气泡**（`deliver-pipeline.ts` 的 `audioFileToSilkBase64` → `sendVoice`），故声明 `{ synthesisTarget: "voice-note", transcodesAudio: true, captionedFinalText: false }`——`captionedFinalText: false` 是必需的：QQ 语音消息**不带文字说明**，声明为 true 会让框架把终稿正文 defer 成语音附注文本（`shouldDeferFinalTtsText`）而正文永不到达。**注意 `capabilities.nativeCommands` 刻意不声明**（见「指令面板自动同步」条目：QQ 指令面板是引导型 UI，声明它会与 `commands.text=false` 的文本斜杠指令路由语义冲突）。

- **Multi-account**: top-level `channels.qqbot.appId/secret` is the `"default"` account; additional accounts go under `channels.qqbot.accounts.<id>`. Each account gets its own gateway and token cache. OpenIDs are **per-account** — a user OpenID from bot A cannot be used by bot B.

- **改配置面必须同步 manifest 的 channelConfigs schema（2026-10-22 stream-all 事故）**：`channels.qqbot.*` 配置校验的**唯一来源**是 `openclaw.plugin.json` 的 `channelConfigs.qqbot.schema`——顶层一份 + `accounts.<id>` 段一份（映射值里再嵌一份），两处必须逐字一致；框架对通道配置走 `validatePluginSchemaValue`（`applyDefaults: true`），**对 `additionalProperties:false` 和 `enum` 都做值校验**。改 `src/types.ts` 的配置类型——加字段、加枚举成员、改嵌套子字段名——而不跟 schema，等于**用户配置被直接拒收**：typecheck 不设防（类型是插件自己的），字段名级守卫也拦不住枚举成员增删（v2.8.0 前 `sendMode` 加 `'stream-all'` 没跟 schema enum，用户一配就被拒，功能有代码无入口；`clientSecretFile` / `groups.tools` 是同款事故的字段名变体）。守卫在 `tests/manifest-config-schema.test.ts`：① 嵌套子字段名 ↔ TS 接口键清单对照 ② 映射值型字段（`groups`/`accounts` 的 additionalProperties 包值）单独穿透一层 ③ 字符串枚举值级对照（TS 联合类型 ↔ schema enum 双向相等）④ 每个枚举成员过**真实校验器**（schema-validator 的实例校验，与框架 `validatePluginSchemaValue` 同源）——**新增枚举/字段后守卫红了，先补 manifest，不要绕过守卫**。

- **Group message priority chain**: `groups.{groupOpenid}.requireMention` → `groups.*.requireMention` → account-level `defaultRequireMention` → `true` (default). Same precedence applies to other group config fields (`ignoreOtherMentions/toolPolicy/name/prompt/historyLimit/historyMode/unmentionedInbound/coalesce` all use the same ??-cascade).

- **指令面板自动同步** (`src/features/command-panel.ts`, 挂载于 `initFeatures`): gateway ready 后把 openclaw **tier=essential 原生指令**注册到 QQ Bot 指令面板（`/v2/panels`，2026-08-12 平台新接口，经 SDK `bot.api` 通用网关调用，无需 SDK 类型化封装）。c2c/group 各一个面板（`target_type=all`），自家面板用 `panel.remark = "openclaw-qqbot:auto:<scope>"` 打标做幂等识别——**remark 不匹配的面板（用户手建的）绝不触碰**。平台约束：name ≤14 字符（`/export-session`、`/export-trajectory` 因此被跳过，最终 8 项）、desc ≤30、每面板 ≤20 项、POST 限 10 QPM。面板 `command` 项点击只是**把指令文本填入输入框**，用户发送后以普通文本进框架走文本斜杠指令路由——所以插件**不声明 `capabilities.nativeCommands`**（QQ 无结构化调用事件，声明反而与 `commands.text:false` 冲突）。配置门控 `channels.qqbot.commands.native`（默认 true）；每进程每账号只同步一次（防 `resumed` 重连重复触发，失败释放 guard 待重连重试）；失败只记日志绝不阻断启动。
