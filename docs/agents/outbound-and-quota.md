# 出站投递、配额与分块

> 深度参考文档。改发送路径 / 配额扣减 / 文本分块前必读。

- **QQ 语音（语音条）投递口径以「体积」为准，不是「时长」（2026-10-20 核实官方文档）**：官方《富媒体消息概述》给的富媒体限制是**体积制**——`file_type` 1 图片(png/jpg) 软 20MB / 硬 200MB、2 视频(mp4) 软 30MB / 硬 200MB、**3 语音(silk) 软 20MB / 硬 200MB**、4 文件 200MB，「**超过软限制会降级为文件类型上传，超过硬限制会报错**」。**平台文档里没有任何语音时长（秒）限制**——「60 秒以内是语音条」是体积与时长的相关性错觉（TTS 语音通常只有几百 KB～1 MB，远低于 20 MB）。平台只把 **silk/mp3/wav/ogg** 渲染成语音条。**我们代码侧的口径此前与平台不一致**：`inferMediaKind` 把 `.amr/.flac/.aac/.m4a` 也判成 voice（平台不认 → 被隐式降级成文件卡片，还丢掉我们设的文件名），且语音**不做体积检查**、纯靠平台隐式降级。现已对齐：格式只认 4 种，语音超 20MB 软限制由 `resolveOutboundMediaKind` **显式**降级为文件投递（结果与平台一致但可预期、文件名可控）。另：官方《消息类型》页明确**表情表态仅频道支持**（单聊/群聊 ❌），故 `capabilities.reactions: false` 是对的。

- **出站锚点模型：显式锚点 or 主动（2026-11-03 移除池化选取）**: 挂 msg_id 的被动消息在平台语义上是「**对用户消息的回复**」（官方《消息收发概述》），锚点必须来自显式回复意图——网关 `resolveOutboundAnchor`（qqbot-gateway.ts）只透传显式 `opts.msgId`（quotaReserved 链：dispatch/deliver 的 turn 锚点、进度卡 passiveOnly 等，`msgSeq` 一并透传）；**无显式锚点（message 工具不带 replyTo、remind/cron 定时投递、框架直发通知如 💾 Learned）一律不挂锚点、走主动发送**（`recordProactiveSend` 计入每日预算）。**红线：禁止重新引入「从缓存挑 msg_id」的池化选取**——历史上为省主动预算引入（`7a59a2c` 取最新 → `bbed520` passive-first → `e3e2be7` 旧配额优先），但它把无上下文发送挂到更早的入站消息上=把回复引用挂到错误的消息，2026-11-03 按平台语义移除。**ask_user 问题卡同样走显式锚点（2026-11-05）**：单题卡 / 多题卡 / 确认卡 / 状态回执此前走 SDK 直发（请求体不带 `msg_id` ⇒ 平台按**主动消息**处理）——白烧每日 1000 条主动预算，且用户关闭「允许主动发送」时问题卡根本发不出去（纯文本兜底同样是主动），模型只能空等 `ask_user` 超时（默认 900s）。现改走 `outbound-service.sendText` + 本轮 inbound 的显式锚点（`envelope.messageId`）⇒ 被动回复；锚点不可用（本地 TTL 预检 / 平台判死 40034005·40034128）时**降级为主动发送一次**（`src/outbound/question-send.ts`，与 Progress Card 同口径，降级时**保留 keyboard**）。多题的续卡 / 确认卡 / 状态回执复用登记在 pending 里的**同一锚点**（群聊 TTL 仅 5min ⇒ 用户迟迟不答时续卡会降级主动，属已知残留限制）。**红线：禁止改回 SDK 直发**（不带 msg_id 即主动形态）；**不得**让网关 `retryOnDeadAnchor` 兜底（那条主动重发路径走 `bot.sendText`，不携带 keyboard）。**代价（有意接受）**：无锚点发送消耗每日 1000 条/关系主动预算；用户在 QQ 客户端关闭「允许主动发送」时该类消息平台拒发；群主动受 20/qpm/关系限频——靠 proactive-budget 80% WARN 与 `/bot-group-info` 观测。显式锚点的配额/发号机制全保留，且自 2026-11-03 起按**反应式配额**工作（详见下一条 bullet）：quota-manager 只对 TTL 窗口/死锚点做本地预检，**次数不再本地阻断**，消耗即发号 `msg_seq`（per-(account,msgId) 单调、从 1 起、失败只回滚观测 count 不回退 seq；经 `bot.send` 的 `extra.msg_seq` 显式下发，替代 SDK 准随机注入——SDK 仅在 body.msg_seq undefined 时注入；markdownSupport 分支与 `bot.sendText` 等价，`sendRaw` 自动补 msg_type）。入站 `cacheMsgId`（event-handlers）以**平台事件 timestamp**（`Date.parse`，NaN 回退本地时钟）登记（msgid-cache 现仅为「接收时刻登记表」：供诚实重建与死锚点簿记，**不再是锚点池**）并 `registerMsgIdWindow` 预注册配额窗口（幂等，防重复推送重置；窗口**起点**锚定平台时间，比对仍用本地时钟，本地与平台若有偏差 Δ 会等量放宽/收紧判定，并非时钟无关），窗口 TTL `PLATFORM_PASSIVE_WINDOW`（c2c 60min/group 5min）。配额缓存容量控制：超限**先清扫过期条目**（含窗口已过的 dead 锚点）再按插入序 FIFO 淘汰，消耗/探测触达把活跃条目沉到队尾（LRU）；条目被淘汰后消耗侧重建窗口时以 msgid-cache 登记的真实接收时刻为准（`checkAndConsume` 的 `receivedAt` 参数，**诚实重建**，不再无声以当下起算；无从得知接收时间时退回 now+TTL 并打 DEBUG；重建会使 seq 归零，锚点失效兜底自愈）。**锚点失效兜底**：被动发送被平台 **40034005（msg_id 已过期）/40034128（超限）**确定性拒绝（`ApiError.bizCode`）→ rollback + `evictMsgId` + `invalidateMsgIdQuota`（置 `dead` 标记，rollback 不得复活）→ 同内容**转主动重发一次**（计入每日预算）；网络错（`httpStatus===0` 结果不明，重发有重复风险）与其他业务码不重发；**`passiveOnly` 发送（progress card）在网关层不做主动重发**——清理死锚点后原错误上抛，由**上层卡片发布器**决定降级主动（`allowActiveFallback`，见 Progress Card bullet）；残余主动发送按账号计数于 `src/features/proactive-budget.ts`（跨天重置，80% 告警，`/bot-group-info` 展示）。**msg_seq 已知残余**：媒体路径（SDK sendMedia 无 seq 透传位）与 **typing**（SDK sendInputNotify 同样无透传位，c2c 每 20s 续期+出站后 5s 补发）仍走 SDK 准随机 seq——同 msg_id 上小概率与插件单调序号碰撞（单次 ~4/65536，失败回滚下次自愈）；typing 自 2026-11-03 起不消耗配额（纯存活探测），不再引起计数器跳号；排障时勿按「seq 已完全受控」假设推断。

- **反应式配额（2026-11-03 重构）**: 此前本地按文档口径「C2C 4 次/msg_id/60min、群 5 次/5min」preemptive 阻断——2026-11-02 探针实测（官方 WebSocket 收 C2C + 撤回接口自证）**平台并不执行该次数上限**（同一 msg_id 连发 25 次被动回复全部送达，25s 慢速复测同样全过；typing msg_type=6 也不占额度）。本地 preemptive 阻断等于替平台做决定：逼正文降级主动、白烧每日 1000 条主动预算、进度卡被静默跳过。现模型：**count 仅观测**（超文档上限打一次 INFO 留证，`overLimitLogged` 每 msg_id 一次），本地仍强制的只有两个平台真实硬约束——① TTL 窗口（c2c 60min/group 5min，过期=40034005 确定性拒绝，预检省一次必败请求）② `msg_id+msg_seq` 唯一性（40054005，消耗即发号单调 seq）。**平台若真的拒绝**（40034005/40034128）→ 网关 `retryOnDeadAnchor` 剔除死锚点 + 同内容转主动重发一次（`passiveOnly` 在网关层不重发，原错误上抛；卡片由上层降级主动，typing 则本轮停发）——反应式兜底的核心就是这条既有机制。API：`checkAndConsumePassiveReplyQuota()`（存活预检+发号+观测计数，rollback 只修观测 count）与存活探测 `checkPassiveReplyQuota()`（typing 等用，只判 TTL/dead）；`getPassiveReplyQuotaRemaining` 已删除（保槽语义随本地次数门一起失效）。`ReplyLimiter`（src/outbound/reply-limiter.ts）是独立的老工具类，与 quota-manager 无关。

- **Typing renewal**: C2C typing indicator (`sendTyping`) automatically renews every 20s minimum (QPS constraint). typing（msg_type=6）**不占回复额度**（探针实测），只做锚点存活探测（`probePassiveAnchorAlive` → `checkPassiveReplyQuota`，判 TTL/dead）——**锚点过期/判死 ⇒ 本轮停发**（2026-11-03 起不再降级为不带 msg_id 的主动形态：主动额度留给正文与前置消息，typing 不参与竞争）。平台当场拒收 typing（40034005/40034128）同样停发，并 `invalidateMsgIdQuota` 标记死锚点（本轮后续消息一律不得走被动回复）。turn 内中间件（`src/middleware/typing.ts`）与心跳路径（`src/typing-lifecycle.ts`）**同口径**；框架出站适配器 `canSendTyping` 本就是「锚点不可用即 false」。Typing also auto-renews after outbound messages (5s delay) to maintain the indicator during streaming/chain-of-thought. See `c2cTypingIndicator` middleware and `POST_MESSAGE_REFRESH_DELAY_MS` constant.

- **Progress Card 逐条快照（2026-10-08 新增）**: agent 的 `progress_card` 工具（会话级 checklist，整体替换式更新）每次成功更新 → 框架 plan 事件 → dispatch 的 `replyOptions.onPlanUpdate`（telegram 同款契约）→ `ProgressCardPublisher`（src/outbound/progress-card-publisher.ts）渲染卡片快照作为**独立 QQ 消息**逐条发送——QQ 无消息编辑 API（telegram 是单条 draft 反复 edit），流式 update 只接受前缀增长、checklist 状态变化必然改行，做不到合并。**双形态**（2026-11-03 note 形态支持）：框架把工具调用投影为 plan 事件（`projectProgressCardChannelUpdate`，progress-card-channel-summary）——① checklist 形态（带 plan）→ steps + 自动计数 explanation → `📋 进度 N/M` 头 + ✅/▸/▢ 行（**框架自动计数行 "N/M complete" 被抑制**——与头重复）（复用 SDK 共享渲染器 `formatPlanChecklistLines`，`openclaw/plugin-sdk/channel-outbound`——**注意 2026-10.2 已整体移除 `openclaw/plugin-sdk/channel-message`，该 import 必须走 channel-outbound**）；② **note 形态**（仅 markdown，框架引导的**首选形态**——可测量工作 prefer a leading progress bar、阻塞状态 in markdown and omit plan）→ 框架剥格式折叠为纯文本单行放 explanation → `📋 状态` 头 + note（截断 `NOTE_MAX_CHARS=300`，**字形簇安全切点**——复用 `outbound/grapheme.ts` 的 `resolveFindGraphemeChunkEnd`，禁止按码元硬切切碎代理对）；③ 清卡（双空）→ steps=[] 无 explanation → 不发消息、抑制发布。**判定式**：`steps=[] && explanation 非空` 即 note（框架保证 steps>0 时 explanation 恒为自动计数 "N/M complete"，无歧义）；此前 steps=[] 一律当清卡会让 note 形态被静默丢弃。**已知限制（插件侧无解）**：混合形态（plan+markdown）的 markdown 叙事在框架投影层就被丢弃（explanation 被自动计数覆盖），插件只能收到 steps。**配额口径（2026-11-03 反应式化 + 卡片降级主动）**：卡片**先走被动回复**（`passiveOnly`）——本地**无次数门**（保槽 `reserveQuota` 已随本地次数上限一起删除，2026-10-08 引入的「探测剩余 ≤ reserve 即丢弃」机制整体退役；平台实测不执行 4/5 次上限），唯一本地保险丝是 `maxPerTurn`；**锚点无存活（无 msg_id/TTL 过期/判死）或平台判死（40034005/40034128）⇒ 降级为主动发送一次**（`allowActiveFallback`：不挂锚点、不走 passiveOnly ⇒ 计入每日 1000 条主动预算，用户仍能看到进度）——卡片按「前置消息」处理，与正文/流式分段同等待遇。**降级状态本轮记忆**（`anchorLost`）：后续快照直接走主动，不再重复被动尝试与本地拦截刷 WARN。**底层 `sendText` 仍永不主动降级**（`passiveOnly` ⇒ 返回 `{error:'passive-quota-exhausted'}`、不触达网关；死锚点被平台拒绝时剔除死锚点后原错误上抛）——**是卡片发布器上层**请求 `allowActiveFallback` 才走主动，别把 passiveOnly 读成「这条消息永不变主动」。发送失败=丢弃（WARN，不重试、不计入「用户是否收到可见回复」判据）。**回调解锁标志**：`replyOptions.suppressDefaultToolProgressMessages: true`——verbose 关闭时 onPlanUpdate 转发的必要条件（quiet channel-owned progress；该标志本身不抑制任何东西，抑制框架默认计划状态消息的是另一个标志 `suppressToolProgressMessages`，刻意不传保持 verbose 现状）；room_event 群不传 `allowProgressCallbacksWhenSourceDeliverySuppressed` → 框架不转发 plan 回调 → 结构性无卡片。**停止时机**：deliverHandler 收到首个非 `kind='tool'` 投递（final/媒体/ask_user；`'tool'` 是 verbose 状态通知不算）即 `stop()` + `await drain()`（等 in-flight 发送落地再放行正文，防「卡片晚于答案」），dispatch 末尾 `dispose()`。**防抖语义（Sourcery 本地拦截 / 平台 40034005·40034128 判死）**不记**——降级主动重发成功才计入 sentCount（降级重发只计一次，不重复计数），且降级状态本轮记忆（后续快照直接走主动，不逐快照重试刷 WARN）；**清卡重置去重**（恢复同文本 checklist 重新发布）。（`resolveQuotaAccountId` 已随配额探测删除——它存在的唯一理由就是给探测提供与记账一致的账号键。）**时序陷阱**：mock dispatchReply 立即返回会先触发 dispose——测试必须在 dispatchReply mock 内部触发 onPlanUpdate/deliver（模拟 run 进行中），见 tests/progress-card.test.ts 的 midRun 手法。配置 `channels.qqbot.progressCard`（enabled/scope/minIntervalMs/maxPerTurn/maxLines，默认 c2c 启用、群关、1500ms 防抖、每 turn 3 条、8 行；`reserveQuota` 已删除——配置残留会被 schema 拒收，升级需移除该键）；restricted 群默认工具集已含 `progress_card`。**Adoption 提醒**：纯通道 Gateway 框架不注入 progress_card reminder——要 agent 主动用卡，需在其 AGENTS.md/SOUL.md 自行引导。回归测试 tests/progress-card.test.ts（52 用例）。
