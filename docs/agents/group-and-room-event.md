# 群聊、room_event 与合批

> 深度参考文档。改群聊策略 / 合批 / 历史窗口前必读。

- **群聊三模式矩阵（2026-09-09 群聊架构改造）**: 群主把 bot 拉进群时选推送模式（**插件不可控、同账号各群混合**）：(1) **AT 纯模式**——仅被 @ 时收到 `GROUP_AT_MESSAGE_CREATE`；(2) **AT+最近N（≤10）**——@ 事件的 `msg_elements` 携带最近消息记录（`MsgElement` 含 per-element author、message_type 102=聊天记录；示例3 为预渲染文本 `=== 消息 N ===`）；(3) **全量模式**——每条消息推 `GROUP_MESSAGE_CREATE`。两事件共用 intent `GROUP_AND_C2C_EVENT`(1<<25)、SDK 映射为同一形态（仅 `rawEventType` 保留）、走同一条中间件链——插件**无需也不应按模式分流**，per-group 模式推断存于 `src/features/group-mode-store.ts`（模式变化打 `[group-mode]` INFO），`/bot-group-info` 命令展示推断+生效配置（排障"这群为什么没上下文"）。msg_elements 渲染在 body-assembler `buildMsgElementsContext`：预渲染文本直通（防 `=== 消息` 二次包裹）、quote 与其余元素并列渲染（quote.source==='msg_elements' 时跳过第 0 个元素）、元素级 attachments 渲染 `[附件]` 行。

- **群消息排队交给框架（coalesce.enabled）**: 消息**逐条立即 dispatch**，排队/合并由 openclaw followup 队列承担：dispatch 侧为群 turn 传 `replyOptions.queueModeOverride`（`coalesce.enabled=true`→`'collect'` 合并批处理；`false`→`'followup'` 排队不合并——尊重"关合并"意图且远比框架默认 steer 安全）。插件内建 coalescer 已删除（不再有 `strategy:'plugin'` 回退路径）。群 turn `admission` 从 `cancel-only` **修正为 `'exclusive'`**（框架约定 durable ingress 用 exclusive；cancel-only 是 gateway chat.send 的取消身份语义）且仍不传 abortSignal——"不打断正在处理的 turn"由框架队列保证（room_event/collect 均 `shouldSteer=false`）。session key 保留 `:coalescing` 后缀（纯历史遗留命名，框架侧无语义，保存量会话 lane 不断）。每进程首条群消息打 `[queue]` INFO 确认接管。

- **room_event 完整支持（2026-10-20 重构；全量群 opt-in，默认关）**: 策略裁决集中到 `src/features/room-event.ts`（唯一入口 `resolveGroupRoomEventPolicy`），门控（policyInjector）、入站分类（dispatch）、历史缓冲跳过（middleware/gateway）三处共用同一份结论——**三处各算各的必然出事**（门控放行 + 分类成 user_request = 刷屏；门控拦掉 + 分类成 room_event = 永远收不到消息）。**回落链**（对齐 openclaw 10.5 框架裁决）：群级显式 `groups.<id>.unmentionedInbound` > `agents.entries.<id>.groupChat.unmentionedInbound` > `messages.groupChat.unmentionedInbound` > `user_request`（群级「未配置」与「显式配 user_request」必须可区分——靠 `ResolvedGroupConfig.unmentionedInboundExplicit`，不能拿带默认值的解析结果去回落，否则框架级配置永远不生效）。**可见回复模式按 turn 判定**（不是按群）：room_event turn → `message_tool_only`（结构性沉默：最终文本不投递、只放行 `message` 工具）；user_request turn → 配置驱动，**且按会话类型隔离**（群/频道读 `messages.groupChat.visibleReplies`，非群只读 `messages.visibleReplies`——框架 c2c 分支同样不读 groupChat，混读会把「群里配 visibleReplies=message_tool」扩散到私聊、把 DM 终稿压成静默）——同一群里两种 turn 交替出现，按群判定会把「被 @ 的那条」也压成静默（用户 @ 了 bot 却没回音）。**message 工具守卫（防结构性沉默，2026-10-06 事故同类）**：room_event 的唯一发声通道是 `message` 工具，而框架的 `messageToolAvailable` 降级**不覆盖 room_event 分支**（core 的 room_event 分支直接 return message_tool_only，两版皆然）→ 插件侧自行保守判定（群 / agent / 全局的**显式非空** allow 白名单不含 message，或 deny 含 message 或 `*`；**allow 缺失/为空 + alsoAllow 非空 = 不限制**——core `unionAllow` 会合成 `["*", ...alsoAllow]` 隐式全放行，按排他白名单判会与框架结论相反、把能说话的群误降级），**确定不可用时该群自动降级回 user_request**（恢复正常回复权）+ 每群一条 WARN；用户可用 `groups.<id>.roomEventRequireMessageTool: false` 关掉降级（显式选择严格静默）。判定只针对「确定」的情况，未知 profile 一律按可用（宁可多跑一次 turn，不误伤能说话的群）。**agent profile 不是阻塞项**——core 在 `message_tool_only` / `room_event` turn 会把 `message` 强制并入 profile 允许集（`runtimeProfileAlsoAllow`，9.1 与 10.5 一致），故 `minimal`/`coding` profile 的 agent 在房间里**依然能说话**；早先按 profile 判不可用会把这类群误降级，已修正。**唤醒判定唯一口径**（`resolveWakeDecision`）：@（SDK mentionGate）/ 引用 bot（SDK implicit）/ 称呼（mentionPatterns）三合一——此前 body 组装只认 SDK 标志，导致称呼唤醒既无 `(@you)` 标记也拿不到群历史；**称呼唤醒现在也穿门控**（`buildMentionGateResolveConfig`：mentionPatterns 命中即放行到 dispatch——普通群此前根本到不了分类逻辑，README 承诺的「三种唤醒方式」名不副实，只有 room_event 群因门控全开才生效），门控判定落 `ctx.state.nameMentioned` 供 dispatch/body 复用（门控跑在内容清洗之前，两处各算各的会漂移）。**room_event turn 不发失败兜底**（provider 抖动会刷屏；同群被 @ 的 turn 仍发正常兜底）。**历史去重**：room_event 群 historyBuffer 的 groupKey 返回 undefined（每条消息已进框架持久化 transcript，插件快照会造成双份上下文），gateway 出站历史记录同步跳过——两处都读**裁决后**的策略（只看群级配置会漏掉 per-agent/全局开启的群，该群会同时存在 transcript 与历史快照两份上下文）。成本提示：每条消息一次推理 pass，collect 批量缓解；务必配 rateLimiter（见下）。**message 工具出站红线**：`channel.ts` 的 `qqbotThreadingAdapter.buildToolContext` 必须返回 `{currentChannelId, currentMessagingTarget}`（从 `context.To` 透传限定目标 `qqbot:group:{gid}` / `qqbot:c2c:{openid}`）——返回 undefined 会让 message_tool_only 的隐式当前来源发送落入框架 **internal-ui sink**（WebUI 显示 "Sent visible reply ... via internal-ui"，只进 openclaw 会话记录，QQ 侧无消息、无出站 HTTP 请求，2026-09-09 用户反馈事故；回归测试在 tests/room-event.test.ts）。**群工具策略红线（2026-10-06 线上事故，openclaw 2026.9.6+）**：框架会把 `qqbotGroupsAdapter.resolveToolPolicy` 的返回值作为会话工具策略**真正应用到 run 的工具集**——`{allow: []}` 空允许清单 = 什么都不允许（连 message 工具都被过滤）→ room_event 群彻底沉默（message_tool_only 下发言唯一通道被切断；≤9.5 框架不应用该返回值，旧 `restricted→{allow:[]}` 映射当时无害）。**工具策略来源已重构为配置驱动（2026-10-06）**：用户可通过 `channels.qqbot.groups.<groupId>.tools.allow` 声明自定义工具白名单，插件直接透传（支持 alsoAllow/deny 合并、toolsBySender 按发送者精细控制）。未声明 tools 时按 toolPolicy 兜底：full→undefined；restricted（默认）→ 插件内置默认工具集（message/web_search/web_fetch/x_search/session_status/heartbeat_respond/view_image/tts/cron/qqbot_remind）；none→显式全禁。且框架回调 adapter 的 groupId 派生自 session key（**小写**），QQ openid 配置键原生**大写**——`resolveGroupConfigFromAccount` 必须大小写不敏感查找（`lookupGroupEntry`，对齐框架 `resolveScopeKeyCaseInsensitive`），否则 adapter 路径永远落默认值。线上应急：给群配置**同时配大写与小写两个键**（或仅小写键）`toolPolicy: "full"`。回归测试 tests/group-tool-policy.test.ts。

- **openclaw 10.5 会主动外发「💾 Learned:」通知（2026-10-20 定位，非缺陷，不修）**：10.5 新增的 Skill Workshop（自学习）后台复盘在改动 skill 后，会向**触发它的那次会话**发一条 `💾 Learned: updated \`xxx\` (…). Say "undo" to revert this skill change.`。逐版本核对 dist 确认：**9.1 与 10.1–10.4 都有后台复盘、但都没有「外发通知」这一步**（10.5 才加的 `postWorkshopChangeNotice`，在 `dist/experience-review-*.mjs`）。要点：**(1) 默认就是开的**——`skills.workshop.autonomous.mode` 默认 `"auto"`（`resolveSkillWorkshopConfig`）；**(2) 群聊同样会收到**——投递判定只有「渠道可投递 + 有 `target.to`」两条，**没有「是不是群」的条件**，且这是**框架主动外发**的出站消息、**不经过入站中间件链** → 群的「仅被 @ 才响应」（`requireMention`）对它无效；**(3) 投递目标从持久化会话 entry 的 `delivery.context` 读**（不是现场解析 sessionKey），`chatType` 只被记录、**不参与投递判定**；**(4) 在 QQ 侧按主动消息发送**——payload 只有 `{text}`、不带 `replyToId` → 不吃被动回复配额，走 QQ 主动消息通道（受其频率/风控限制）。规避：`skills.workshop.autonomous.mode: "off"`（`skill_workshop` 工具本身仍在，agent 主动 `/learn` 不受影响），或用 tool policy 按**群 / 发送者维度**禁 `skill_workshop`（准入检查在 `prepareSkillExperienceReviewCandidate`，policy 链含 `groupPolicy` / `senderPolicy`）。

- **群历史模式 historyMode**: 默认 `clear`（回复后整清，"自上次回复以来的窗口"）；`rolling`——bot 出站也记入 historyBuffer（gateway `storeEntry` 附 `isBot:true` 条目），回复后 `trimGroupHistoryAfterLastBot` 裁剪到最后一条 bot 发言之后（对齐 telegram selectAfterLastSelf，AI 下次可见自己上次说到哪）。

- **群消息合并在插件侧做（2026-10-23）——框架的 collect 合批对「同群不同人」无效，插件自建 busy 信号**。框架 followup 队列的 `collect` 模式**合并不了跨发言人的群消息**：其分组键含 `execution.senderId`（core `resolveFollowupAuthorizationKey` → `resolveFollowupDeliveryStorageKey` → `prepareNextDeliveryGroup`），且该函数**遇到第一个 key 不同就 break** ⇒ 只有「连续同 key」才成一批。故插件自建合批：`src/features/group-session-busy.ts`（per-群 in-flight 计数——**框架没有向通道插件暴露 busy 查询 API**，但插件知道：`dispatchToOpenClaw` 里 `await adapters.inboundRun!()` 在**该 turn 被采纳并跑完**时 resolve；⚠️ 被框架 **defer**（排队）的 turn 在**仅入队**时就 resolve ⇒ busy 提前归零（已知退化，非正确性破坏——消息仍送达、顺序不变，只是没被合成一轮））+ `src/features/group-merge.ts`（用框架现成的 `createInboundDebouncer`：`shouldHoldFlush` 恒 true ⇒ 静默期到点后继续压住并重排定时器（无限期持有），`flushKey` 是**显式冲刷、绕过 hold 检查**；turn 结束（计数归零）→ 冲刷 ⇒ 攒批一次性发出。**批次键按群**（不是按人））。**busy 标记必须紧贴 try/finally**（评审修复）：早前放在函数入口，与 finally 隔着数百行同步代码，其中任一处同步抛错都会让 finally 不执行 ⇒ 该群 busy **永久为 1** ⇒ 之后所有群消息只能靠 `maxHoldMs` 兜底放出（系统性延迟 5 分钟，静默无感）。合并内容走 `assembleMergedGroupBody`（body-assembler）：**不能直接拼 N 条 agentBody**——`buildAgentBody` 在「群被@且有历史」时给每条各加一份 history 块，拼起来历史重复 N 份；且 **SDK 的 `historyBuffer` 暴露的 `ctx.state.history` 是「不含当前消息、但含此前所有消息」的快照** ⇒ 取「最新成员」的快照会让批次内非最后一条成员**被说两遍**（历史块 + 自己的分节）——历史必须取**批前基线**（最早成员的快照）。c2c 侧同款缺陷已一并修（`mergeAssembledBodies` 只保留第 1 条那份历史块）。批内任一条「在叫 bot」则整批按 user_request 投递（否则「用户 @ 了 bot 却没回音」）——**置位必须在装配之后**，否则载体会被虚标 `(@you)`（归因误导）。旁路不合并：控制命令 / 斜杠命令（**同时看原始与清洗后两份文本**——单条路径的命令直通用清洗后的 userContent，只看原始会漏 `@bot /cmd`）/ ask_user keyed 答案 / **stt·fallback 来源语音（真实音频语义）——平台转写语音（全部 transcript `source:'asr'`）= 纯文本，参与合批**（2026-11-01 修复：此前任何语音都旁路，忙时语音不但自己单独成 turn，还会触发 debouncer「旁路项先冲刷 pending buffer 再单独发」把已攒的文本批拆散；旁路的原始理由——对齐框架 `requiresIndividualCollectDrain` 的 `currentInboundAudio`——经查是错误粒度的镜像：该约束作用于框架队列**多个 pending item 之间**的 collect 合批，插件合成单条 turn 反而减少队列 item、不触发该路径；合批判定在中间件链链尾，此时平台转写已就绪，语音成员渲染 `[消息 i/N]` + `[昵称 (openid)] [Voice message] <全文>`，audio media fact 经 `mergeProcessedAttachments` 保留且框架侧惰性——`transcribed:true` 不产 prompt 媒体注记、不二次转写）。默认最多 10 条 + 8000 字双上限，超出**丢弃较早的**并在前置一行 `[已丢弃 N 条…]`（与框架 `[Queue overflow]` 同样式）。空闲时**零延迟**直发。配置 `channels.qqbot.groupCoalesce` / `groups.<id>.coalesce`：`strategy`（`'plugin'` 默认 / `'framework'` 回退框架队列）、`maxBatchSize`、`maxHoldMs`（**对「直到 turn 结束才发」的兜底偏离**——turn 挂起时批次滞留内存且随重启丢失；`0` = 永不强制）。守卫 `tests/group-merge.test.ts`（32 例）。

- **`#ROBOT1.0_<id>! ` 前缀是框架把消息 id 合并进正文，不是平台塞进 content（2026-10-23）**。现象：Web UI 群消息气泡正文形如 `#ROBOT1.0_xxx! 土豆马铃薯: 大肥鱼`。**平台层 id 与正文是分开的**（官方《群消息（全量模式）》：id 是事件体独立字段、被动回复锚点 `msg_id` 同形，`content` 定义里没有 id 前缀；QQ SDK 原样透传 `ev.content`；插件与框架都没注入过）。真正的注入点是 **openclaw 框架的 `formatRoomEventLine`**（core：`prefix = [messageId ? \`#${messageId}\` : undefined, sender].join(" ")` → `` `${prefix}: ${body}` ``）——它把 room_event 的 transcript 正文渲染成「id + 发送者 + 正文」一行。**修复方向是改写格式而非剥离入站正文**（入站 content 里本来就没有它，剥是剥错地方）：插件经 ctxPayload 的 `extra` 传 `AmbientTranscriptBody` / `AmbientTranscriptMessageId` / `AmbientTranscriptTimestampMs`（框架 `buildChannelInboundEventContextValue` 末尾 `...params.extra` 展开进 ctx；core `resolveRoomEventTranscriptBody` 优先取 `ctx.AmbientTranscriptBody`）⇒ room_event 的 transcript 行改用插件自定义正文。**刻意不设 `AmbientTranscriptWatermarkKey`**——框架的 ambient watermark 是 telegram 专属路径（`bot-message` 里 `resolveAmbientTranscriptWatermarkKey({channel:"telegram",…})` 硬编码），generic channel 路径不设这些字段，设了会把一条 telegram 口径的去重路径激活到 qqbot 上、副作用未知。
