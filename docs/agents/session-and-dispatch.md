# Session key 与 10.5 指令 / 投递语义

> 深度参考文档。涉及 session key 构造、路由回退、指令准入时必读。

- **canonical session key 文法（2026-10-22 实测，10.x 硬门槛）**：openclaw 2026.10.x 的 state worker 对 session 写入做 canonical 校验（`validateCanonicalSessionRow`），两条硬性要求：① key 必须满足 `agent:<agentId>:<rest...>` 文法（`parseAgentSessionKey` 非 null，保留字 `global`/`unknown` 除外）——**裸通道前缀 key（如 `qqbot:<account>:<peer>`）直接拒写**；② key 必须等于其全小写折叠形（`normalizeStoreSessionKey`，仅 signal:/matrix: 的 peer id 保留大小写）——**含大写的 key 拒写**。违反即抛 `SessionCanonicalKeyMigrationRequiredError`（提示 "stop the Gateway and run openclaw doctor --fix"），该 session 一切读写瘫痪、dispatch 全部 outcome=error。插件生产路径永远走 `adapters.resolveAgentRoute`（两版都返回 agent: 文法：c2c → `agent:main:main`，群 → `agent:main:qqbot:group:<groupId>`，**且与 9.1 完全一致**——升级不改变 key 形状）；但兜底路由（routing API 探测失败时的安全网）旧版拼 `qqbot:...` 形状，在 10.x 下等于全量静默瘫痪，已改为 `buildFallbackRouteSessionKey`（agent: 文法 + 全小写），由 `tests/fallback-route-key.test.ts` 用**已安装 openclaw 的真实解析/折叠函数**锁定。另注意 `dmScope` 框架默认 `"main"`（两版同）：**所有 c2c 用户共享 `agent:main:main` 一个 session**（与 CLI 主会话同 key）；要多用户隔离需用户配 `session.dmScope: "per-peer"`。

- **session key 的 route 文法是 canonical 之外的第二道门（2026-10-22 评审修复）**：canonical 只保证「key 能被写进 state DB」，**不保证「框架能反解出投递目标」**。框架反解用的是 `parseSessionDeliveryRoute`，文法是 `<channel>[:<accountId>]:<peerKind>:<peerId>`——peer 段之后的所有冒号分段都会被并进 peerId。上一版兜底 `agent:main:qqbot:group:<acct>:<peer>:coalescing` 过了 canonical 校验，却被解析成 peerId = `<acct>:<peer>:coalescing`（accountId 与历史遗留 `:coalescing` 后缀一起混进了 peer 段）→ 框架自发回复（`internal-source-reply`）、投递恢复（`delivery-queue-recovery`）、子代理路由（`sessions-spawn-tool` 直接拿 `route.peerId` 拼 `user:<peerId>`）全部指向不存在的 peer。**框架自己的 key 形状**（`buildAgentPeerSessionKey`）：私聊按 dmScope 分四种（`agent:<id>:main` / `agent:<id>:direct:<peer>` / `agent:<id>:<ch>:direct:<peer>` / `agent:<id>:<ch>:<acct>:direct:<peer>`），群聊按 groupScope 分两种（`agent:<id>:main` / `agent:<id>:<ch>:group:<peer>`）——**群 key 不含 accountId**（框架自身就不按账号隔离群会话，插件的兜底也不该塞）。**修法**：兜底优先用框架原语 `runtime.channel.routing.buildAgentSessionKey`（与 resolveAgentRoute 同源，文法永远跟随上游），框架原语也缺失时才退到本地镜像 `buildFallbackRouteSessionKey`；守卫 `tests/fallback-route-key.test.ts` 用**差分**锁死——本地镜像与框架 `buildAgentPeerSessionKey` 在 dmScope × groupScope 全矩阵上逐字相同，外加 canonical 与 route 两条断言。**教训**：写 session key 不能只过 canonical 校验，要用框架的解析函数反解一遍，确认解出来的 peerId 就是目标 peer。

- **10.5 指令/投递语义实测（2026-10-22，harness 驱动真实 10.5 dist）**：① 框架命令层对插件形状**完全兼容**——用插件真实 dispatch 形状（`dispatcherOptions.deliver` 返回 void、`replyOptions` 带 turnAdoptionLifecycle/queueModeOverride）驱动 `dispatchReplyWithBufferedBlockDispatcher`：空闲会话 `/status` 正常解释并送达 deliver；**忙碌会话 `/stop` 走 dispatch 层 fast-abort（`tryFastAbortFromMessage`，发生在 admission ticket 之前）4 秒级中止并回 `⚙️ Agent was aborted.`**——若生产上 /stop 停不掉、/status 无回复，先查部署侧（插件版本/网关日志），不要先怀疑框架。② **admission ticket 发生在 replyResolver 之前**（reply-timing 阶段 `wait_admission_ticket` 实测 9.9s @ busy）：忙碌会话里非 abort 类指令（/status /help 等）要等活动 turn 结束才被解释——"群里任务跑着发指令没反应"在 10.5 是预期排队语义，不是丢消息。③ 10.5 命令回复经 `markCommandReplyForDelivery`（`commandReply` + `deliverDespiteSourceReplySuppression` 元数据，全局 Symbol 注册表），deliver 回调无需返回回执（void 即可，与 9.1 一致）。
